# Opus 5.5によるGen5復帰後の追加レビュー

Devin CLI、Claude Opus 5.5 High、session `shelled-seal`。ユーザーがPC構成と実測値の送信を明示承認したうえで相談。ツール使用なし、ソースコードの参照なし。Maxは600秒で応答がなく終了し、Highの回答を取得した。

以下は助言であり、新しい実測結果ではない。採否に当たっては次を補正する。

- 起動時の使用頻度に基づくexpert配置は既に実装済み。単に頻度順へ置き換える提案は新規の改善ではない。
- 空きVRAM全量をexpert poolへ回せるわけではない。全体cap90 GiB・追加reserve2 GiB・A1常駐を維持し、3〜4 GiBの追加を無条件に認めない。
- DDR4帯域からの速度上限は、traceの比率が生成中にも当てはまり、対象の重みを毎回DRAMから読む仮定付き。配置やcache hit率を改善するコードまで不可能とする結論には使わない。
- 同一expert反復によるcacheの影響は有力な仮説だが、巡回校正などで実証する必要がある。分担表のfはRAMに存在するmiss数で、SSD missを含む全非VRAM数とは異なる。
- 現行CPU/GPU経路の出力差を、そのまま品質の許容基準にはしない。Orca FP8との品質同等性は未検証。

---

以下の数値は、本文に書かれた値から計算したものだけです。新しく測ったものはありません。仮定を置いた箇所には「仮定」と書いています。

## 1. 品質を変えない短期改善3つ（この順で実施）

**① RAM tierを拡大する（設定変更だけで済む）**
- SSDにしかないexpertは現在169.91−66.67−85.98≈17.3GiBです。RAM tierを95GiBにすると約8.2GiB、97GiBにすると約6.2GiBに減ります。
- 稼働中の空きRAMは、95GiBで13〜15GiB、97GiBで11〜13GiBになる見込みです。97GiBはheadroomの12GiBを割る可能性があるため、90GiB→95GiBと段階的に上げてください。
- 注意点：SSD missの一部をOSのpage cacheが救っている場合、tierを増やすとpage cacheが減り、逆効果になることがあります。host待ちとSSDの実読み出し量を必ず併記してください。
- 採用基準：SSD miss比とhost待ちが下がり、tok/sの中央値が上がること。さらに稼働中の最小空きRAMが12GiB以上で、swapやmajor faultが増えていないこと。

**② CPU分担表を決める（実行中の比較を完結させる）**
- 候補は3つに絞ります：auto（012334567）、floor(f/2)（001122334）、§2の仮定計算による表（011223445）。
- traceからf（その層でVRAMにないexpertの数）の出現頻度を出してください。平均は約2なので、効くのは主にf=1〜3の桁です。

**③ VRAM配置を選択頻度順にし、poolを少し増やす**
- 試験中の空きVRAMは7〜8GiBです。余裕を残してpoolを3〜4GiB増やすと、1GiB≈70expertなので約210〜280expert増えます（全12096個の約2%）。
- 固定seed配置を、選択回数の多い順の配置に置き換えます。過学習を避けるため、配置を作るpromptと評価するpromptは分けてください。

**共通の採用基準（数値は提案値です）**
- 各構成で3課題×5回程度走らせ、初回は捨てて中央値と範囲を記録します。
- 中央値が+3%以上で、かつbaselineのばらつき幅を超えること。どの課題も−2%を超えて悪化しないこと。

## 2. 校正の最小変更

**LLC-hotの根拠**
- 0.103ms/expertは、1expertあたり14.156〜16.318MBなので137〜158GB/sに相当し、DDR4理論値51.2GB/sの約3倍です。1expertがLLC（30MB）に収まるので、LLC-hotと見てよいです。
- DRAMから読むなら理論値でも0.28〜0.32ms/expertかかります。
- traceでもCPU待ちは25.39/42≈0.60ms/層で、CPU担当は層あたり約1.8expertなので、≈0.33ms/expertになります。待ち時間は露出した分だけなので目安ですが、0.3ms前後と整合します。

**変更案（測定は3種だけ）**
- (a) CPU校正を、LLCを超える量のexpert（別層から4個以上）を巡回する方式にしてcoldにします。
- (b) 同時にDMAを流し、競合下のCPU時間c_mixとDMA時間p_mixを測ります。
- (c) 分担の選択式では、k=0にDMA単独値p_solo、k=fにcold CPU値c_cold、0<k<fにc_mix/p_mixを使います。

**仮定計算**
- c=0.30、p=0.423と仮定すると、既存の式は011223445を選びます。
- CPUoffでは全部をDMAに回すのでf×p_soloが最大になり、CPUoffが悪化した実測とも矛盾しません。

**さらに簡単な代替案（コード追加なし）**
- autoのtraceから層ごとの(f, k, CPU時間, DMA時間)を回帰してc, pを推定し、固定表を起動引数で渡します。
- 再現性のため、実行中に分担を動的に変えるのは避けてください。

## 3. 50tok/sの必要条件

**時間の予算**
- 50tok/sは20.0ms/tokenです。現在は67.20ms/passで、1/14.5=69.0msとの差はlayer外の処理です。
- 待ちの合計は52.44msで、残り14.76msはGPU計算などと推定されます。
- 待ちをゼロにしても上限は約68tok/sです。50tok/sには待ちを5.2ms以下、つまり約90%削減する必要があります。

**帯域の制約**
- VRAMにないexpertは25.37%×336≈85expert/tokenで、約1.21〜1.39GB/tokenです（選択比からの近似で、バイト比ではありません）。
- 50tok/sではこれが60〜70GB/sになり、DDR4理論値51.2GB/sを超えます。**コード修正だけでは50tok/sは物理的に到達できません。**

**コード修正だけで期待できる範囲**
- 天井は1.21〜1.39GB÷51.2GB/s=23.6〜27.1ms/tokenで、約37〜42tok/sです（DRAM効率100%で、GPU計算と完全に重なる場合）。
- DRAM効率を仮に0.7とすると、約26〜30tok/sです。
- 現在のexpert読み出しは約18〜20GB/s相当で、帯域にはまだ余裕があります。待ちの多くはlatencyや直列化と見られ、この天井まではコード側に改善の余地があります。

**50tok/sに必要な条件（圧縮かVRAM hit率の変化が要る領域）**
- VRAMにない分を1.024GB/token以下にする必要があります。VRAM hit率で言うと、DRAM効率100%なら79〜81%以上、効率0.7なら85〜87%以上です。
- SSD missは約51MB/tokenで、50tok/sでは約2.5GB/sの実効速度も要ります。
- 必要なVRAM容量は、traceのexpert別選択回数から「容量→hit率」の曲線を描けば求められます（新しい測定は不要）。これで、空きVRAMで足りるのか、down Q6→Q4（10.44GiB削減）級の圧縮が要るのかを判定してください。

## 4. 公平比較と最低限の品質確認

**速度の比較**
- 参照出力を1回生成し、全構成でそのtoken列をteacher-forcingでdecodeして、同じ列でms/tokenを比べます。
- teacher-forcingが未実装なら、EOSを無視して512token固定にします。そのうえでms/pass、VRAMにないexpertの数/token、そのexpert1個あたりのmsを併記し、仕事量の差を補正してください。

**品質の確認**
- 重みは同じなので、差の原因は演算の順序と精度です。CPU経路が活性値を別の精度で量子化する実装なら、その影響も含まれます。
- 同じforced列で、参照構成とのtop-1一致率、平均KL、NLLを比べます。
- 許容範囲は「すでに許容している構成間の差（例：auto対CPUoff）以内」とし、出力全文の一致は求めません。
- 加えて、3課題の出力を簡単に正誤確認してください。
