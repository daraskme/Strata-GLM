# Opus 5.5による比較試験後の再レビュー

Devin CLI、Claude Opus 5.5 High、session `literate-lavender`。
ユーザーが承認したPC構成・メモリ配分・測定値だけを送信。tool呼び出し0。以下は助言であり追加の実測ではない。

採用判断では次を補正する。

- RAM95GiBは比較条件。通常設定は元から可変予算で95GiB前後になり得るため、新しい通常設定の高速化として数えない。
- swap-out不増はカウンターを取った固定plan比較での観測。先に行ったRAM86/95の全探索で測定済みとは扱わない。
- **cacheをFP16へ縮める案はVRAMを解放してexpert領域を増やす方向。回答中の「expert poolのVRAMを削る可能性」は逆であり採用しない。** 長文での検索品質・状態復元は別途検証が必要。
- 転送する重みbyteが同じでも、完了タイミングがcache状態やCPU/GPU割当に影響すれば出力が変わり得る。「品質を完全に検証できる」「token一致ならrouteも必ず一致」は一般には保証できない。route・配置・演算経路を実測で照合する。
- GPUのroute結果はhostへ通知されるが、現行requestは全てのfetch先をhostへ渡していない。DMA試作ではsource/destination、世代番号、完了通知、slot寿命の追加設計が必要。後からrecordするCUDA eventを先にwaitするだけでは今回の転送完了を保証できない。
- workers4/12の速度が近いことだけでDDR律速とは断定しない。IMC帯域や競合実測が必要。
- 50 tokens/sの帯域式は、非VRAMの対象重みを毎回DRAMから読む場合の条件付き。静的coverageを実際の動的hit率へ読み替えない。

次の候補として、CPU処理と競合した状態でmapped readとDMAを比較する事前判定は妥当。
一方、DMAへのランタイム変更、IMC測定、FP16 cache変更は今回まだ実装・測定していない。

# 回答

表記の区別: **【実測】** はいただいた数値、**【仮定】** は未検証の推測、**【未実装】** はまだ作っていないアイデアです。

## 1. 今すぐ採用してよい変更

試行は各条件3タスク程度なので、統計的な確信はありません。採用は「方向がそろっていて、悪化のリスクが低い」という意味です。

**採用する**
- **RAM95GiB(RAM86に代えて)**
  - 【実測】プロファイルありの3タスクすべてで向上しました(+1.1、+1.4、+1.6 tok/s)。swap-outの増加もありません。
  - 条件: 空きRAMの下限ガード、A1のhealth監視、swapの監視は残してください。
  - プロファイルなしでの確認はまだありません。
- **CPUハイブリッドを有効にしたまま、8workersを維持**
  - 【実測】CPUoffとHalf CPU planは3タスクすべてで低下しました。4/12workersは第1タスクで差がありませんでした。
- **評価ではCPU planを固定する**
  - 【実測】auto splitは起動のたびにplanが変わり、比較の条件がそろいません。
  - 012344567と012234556の差は、同じ設定の再測定でのぶれ(タスク3で18.7と21.2)より小さいです。継続性を優先して012344567のままで構いません。本番でauto splitより速いかどうかは未測定です。

**採用しない**
- SSD lookahead2: 結果が混在しています。
- 予測によるRAM→VRAMの1-expert prefetch: 1タスクで低下しました。
- latency-weighted static slot: replayでの差は0.035ppで、速度への因果も未検証です。
- 量子化の変更: 品質が未検証です。
- DMA化: 【未実装】です。

## 2. 次の一手: RAM-tierミス転送のDMA化(go/no-go判定つき)

### これを最優先にする理由
- **改善の余地が実測で見えている唯一の候補です。** 【実測】単体試験でmapped loopは13.6–21.1GB/s、DMAは18.4–31GB/sでした。
- **品質を完全に検証できます。** 転送するバイト列は同じなので、CPU planを固定しT0なら出力tokenが完全一致するはずです。ただしGPUの非決定性がないことは確認が要ります【仮定】。
- **teacher-forced harnessなしで公平に比べられます。** tokenが一致すればroute列も一致するので、同じ作業量での対比較になります。

### ほかの候補より上に置く理由
- **フラグスイープ**: worker数、lookahead、CPU planはいずれもぶれの範囲内で、すでに効果が出尽くしつつあります。
- **forced-decodeベンチ**: それ自体では速度を生みません。routeが変わる変更(量子化など)の評価には将来必要ですが、今回のようにbitが変わらない変更には不要です。
- **cache FP16**: 140token前後の試験はattentionが律速ではありません。品質とメモリの交換であり、expert poolのVRAMを削る可能性があります【仮定】。
- **新量子化**: FP8から作り直す工程と品質評価の基盤が両方必要です。10.441GiBの節約がcoverageをどれだけ上げるかも不明です。

### Phase 0(先に実施する判定)
1. 実デコード中に1tokenあたりのカウンタを取ります: RAM-tierミス数、CPU/GPUへの割当数、転送バイト数、critical path上の転送待ち時間。
2. IMCカウンタで実効DDR帯域を測ります。
3. CPU expertの負荷を同時にかけた状態で、DMAとmapped loopの単体試験をやり直します。
4. **中止条件**: 転送待ちがtoken時間の約10%未満、またはDDR競合下でDMAがmapped loopより速くない場合は中止します。
   - 【実測】worker数を4/12に変えても速度が変わらない点は、DDR律速を示唆しています。

### 実装の範囲
- 対象はGPUに割り当てられたRAM-tierミス転送だけです。CPU経路、SSD経路、キャッシュ方針は変えません。flagは既定offとします。
- 転送元: mapped host領域は登録済み(pinned)と【仮定】し、staging bufferを使わずcudaMemcpyAsyncで直接転送します。
- 専用のcopy streamを1本使い、slotごとにeventを持たせます。
  - 計算streamは、該当slotのeventを待ってからexpert GEMMを実行します。
  - GEMMの後に「消費済み」eventを記録します。evictionはこのeventの完了まで待ちます。
- ルーティングのindexがhostに届いている必要があります。CPU経路のために既に転送されていると【仮定】し、届いていなければ同期遅延を測ります。
- 失敗した場合はmapped loopに戻します。pool容量の66.666GiBは変えません。

### 試験計画
1. 全tierのexpertから抜き取り、slotの内容とバイト比較します。
2. plan固定・T0・seed42で、token IDとlogitのchecksumが完全一致することを確認します。
3. プロファイルなし、6タスク以上をABABで交互に5回ずつ流し、タスクごとの差の中央値と範囲を報告します。
4. VRAM cap、A1 health、swapを確認します。
5. 最後に260K文脈で1回実行します。

## 3. 「コードだけでは50tok/sに届かない」の訂正

これは無条件の不可能証明ではなく、条件つきの帯域の議論です。

**前提の数値(実測値からの計算)**
- 1 expertの平均サイズ S = 169.91GiB ÷ (42×288) ≈ 15.1MB
- 1tokenあたりのrouted活性 = 42層×8 = 336個 → 1tokenあたり約5.07GB
- 50tok/sに必要な時間 = 20ms/token

**条件**
- f(RAM-tierミス率)の分は、CPU計算でもGPU転送でも、DDR4を一度は読む必要があります。
- したがって完全なoverlapでも 20ms ≥ f × 5.07GB ÷ B_DDR が必要です。
  - DDR4-3200 dual channelの理論値51.2GB/sなら f ≤ 約20%
  - 実効37GB/sと【仮定】すると f ≤ 約15%
- さらに、SSDミスがほぼゼロであること、GPU側の計算が20ms内に収まること(未測定)も必要です。

**静的replayの値で当てはめると**
- 静的coverage 68.8%からは f ≈ 0.31 となります。ただしruntimeの実測値ではありません。
- このfなら上限は約33tok/s(理論帯域)、約24tok/s(37GB/s仮定)です。

**結論**
- 50tok/sには、実効VRAMヒット率を80–85%程度まで上げるか、1tokenあたりに動かすバイト数を減らすことが必要条件になります。
- コード(動的promotionなど)でfがどこまで下がるかは未測定です。したがって「不可能」とは言えません。

## 4. 測定が誤解を招きうる最大の2点

1. **ぶれと交絡が、調べている効果より大きいこと**
   - 同じ設定でもタスク3は18.7と21.2で約13%離れています。一方、評価対象の差は数%です。
   - free generationではrouteが変わり、auto splitは起動ごとに変わります。
   - プロファイルありとなしは、試験したタスク自体が異なるため直接比較できません。
2. **マイクロベンチと短い試験条件が、実運用の競合状態を代表していないこと**
   - 【実測】CPU較正値(15MBを0.10–0.15ms)は約94–163GB/sに相当し、DDR4の理論値51.2GB/sを超えます。ほぼ確実にL3 cacheに載った状態で測っており(1 expertは約15MBで、L3容量より小さい)、splitがCPU寄りに偏ります。
   - DMAの単体試験はDDR競合なしで測っています。
   - 静的replayは動的promotionを再現していません。
   - 試験の文脈は140token程度で、目標の260K文脈とは律速要因が変わりえます。
