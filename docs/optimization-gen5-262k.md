# GLM Gen5復帰後の最適化・長文検証

2026-10-09。i9-12900KS、RTX PRO 6000 Blackwell 96GB、DDR4-3200 128GiB、NixOS。
A1を指揮官として常駐させ、OrcaRouter GLM-5.3-Flash Uncensored Q4_K_MをStrataで使う。

## 結論

**A1を残したまま260090 tokensの実入力と512 tokens生成が成功した。3位置検索は全て正答し、生成は17.1 tokens/sだった。**
この確認を受け、Mang-AIの通常GLMを262144枠へ反映し、RAMの予算計算時の余裕を16 GiBへ増やした。
共通APIの日本語・Python関数・tool call検査も成功。持続50 tokens/sと参照Orca FP8相当の品質は未達／未検証。

目標は「262144のコンテキスト枠、持続生成50 tokens/s以上、参照Orca FP8に近い品質」の同時達成。
512-tokenで打ち切ったコード出力を、完成したコードや正答率として数えない。
今回の変更は実行時の分担・先読みを明示設定する仕組みで、モデルの重み、router、量子化形式は変更していない。
それでもCPUとGPUの演算経路の違いにより生成文が変わるため、品質同等性が自動的に保証されるとは扱わない。

## 何を比較したか

- 同じバイナリと同じ重みを使用。GPU expert pool上限66.7 GiB、RAM tier86/95 GiBを指定し、使用履歴seedを凍結した。
- 128Kの枠での短文試験は、入力約140〜150 tokens、生成512 tokens、temperature 0、seed42、思考なし、prefix再利用なし。
- 調整用3課題は区間併合・トポロジカル順序・バージョン解析。未使用だった比較用3課題はstream併合・TTL cache・Dijkstra経路。
- 最初の探索ではCUDA区間計測を有効にし、未使用課題の比較では詳細計測を無効化した。この2群の絶対速度を同じ表の順位として扱わない。
- CPUはPコア側のlogical CPU0〜15、8 workers、idle spin1msを基準にした。4/12 workersも比較。

| auto・RAM95 | 14.4 | 18.0 | 15.8 |

| CPU半数・RAM86 | 10.8 | 11.6 | 12.2 |

**別の3課題（CUDA区間計測なし、CPU分担固定、RAM95）。値はtokens/s。**

| 構成 | stream併合 | TTL cache | Dijkstra経路 |
|---|---:|---:|---:|
| CPU表012344567・先読み0 | 22.2 | 21.2 | 18.7 |

| CPU表012234556・先読み0 | 22.5 | 21.3 | 22.0 |
| CPU表012344567・先読み0の再測定 | 22.1 | 20.8 | 21.2 |

基準の再測定との差は約0.4/0.5/0.8 tokens/sまで縮んだ。基準自身のDijkstraは18.7→21.2と変動しており、固定表の優位は十分に確定できない。
基準と基準再測定は3課題とも出力本文のSHA256が一致した一方、CPU表012234556では3課題とも本文が変わった。同じ文章でも時間が変動し、分担変更では生成する仕事量も変わる点を区別する。
CPU自動分担、8 workers、先読み0、均等slotを通常設定に残した。
起動直後のメモリ回収待ちが足りずguardに拒否された1回は失敗として保存し、性能表には含めない。

RAM95は固定RAM86より良かったが、通常運用は元から空き容量に合わせる可変予算であり、95GiB前後になることがある。
したがって「通常設定を86→95へ変更して高速化した」とは報告しない。固定95GiBは比較条件として使用した。

先読みを有効にして速く見えた最初の結果には、CPU起動時校正の違いが混ざっていた。
起動ごとにCPUの所要時間を測り直すため、同じ「auto」でも分担表が変わる。
実際、先読みなしの比較元は`012344567`、先読み2層の再測定は`012234556`だった。
そこで固定表を使い、先読みだけを変える比較を追加した。単発の最大値で採用を決めない。

## 262144枠での実入力

| 実入力tokens | 出力tokens | prefill | prefill速度 | decode | decode速度 | 3位置検索 |
|---|---:|---:|---:|---:|---:|---|
| 8180 | 512 | 9.77秒 | 837.4 tokens/s | 32.22秒 | 15.9 tokens/s | 3/3正答 |
| 260090 | 512 | 426.49秒 | 609.8 tokens/s | 30.02秒 | 17.1 tokens/s | 3/3正答 |

両方ともcontext設定262144、prefix再利用0。入力の10%・50%・90%付近の合言葉を検索した。
260090入力 + 512生成 = 260602 tokens。HTTP応答まで457.00秒で、モデルの初期ロードは別に約70秒かかった。
容量だけ確保した試験ではない。ただし生成プログラムは512 tokensで打ち切られ、実行正答率を評価していない。
3位置検索は1種類の記録形式・1回の試験であり、実コードの依存関係の把握やFP8との同等性を検証していない。

通常Mang-AIは最大出力16384を維持するため、その出力枠を全て予約するなら入力・template・tool用は245760 tokens以下になる。
262144は入出力の合計枠。今回の性能試験は出力を512に固定している。

| 項目 | 262K固定予算ベンチマーク |
|---|---:|
| GPU dense weights | 5.34 GiB |
| GPU state/KV | 8.74 GiB |
| GPU expert pool | 63.13 GiB、107 slots/層 |
| expert RAM tier | 94.98 GiB |
| 最小空きRAM | 12.62 GiB |
| 最小空きVRAM | 7.15 GiB |
| 観測したGPU総使用量の最大 | 88.44 GiB（A1・画面等を含む） |

prefill用の約6184 MiBはexpert poolから借用される。独立VRAM領域としてもう一度足さない。
CPU側には約996 MiBのpinned landing ring等もある。dense・KV・expert poolの和だけを総使用量としない。

長文試験中、システム全体のswap-outは241541 pages（約943.52 MiB）、swap-inは2478 pages（約9.68 MiB）増えた。
swap deviceは/dev/zram0のみで、SSDへのswap書込と解釈してはいけない。終了後のVmSwap上位には背景アプリがあったが、増加分のプロセス別帰属は測定していない。
「swapなしで運用できた」とはしない。通常設定ではRAM headroomを12→16 GiBへ増やした。これは予算計算時の余裕であり、常時16 GiB空く保証ではない。

A1は全観測でready。算術質問に、GLM起動前0.175秒、長文処理中0.100秒で正答した。
ただし後者は264 input tokens中260 tokensを再利用しており、負荷中の方が速いという比較にはならない。
本格的な指揮タスクのp95遅延は未測定。

30秒間隔の長文観測ではGPU温度最大89℃、電力最大606W。1回の追加確認では電力・温度制限フラグが非作動だったが、全期間で非作動だったことは証明しない。
電力上限、fan、clock、swappiness、zram設定は変更していない。

## 先読み・3段階配置の意味

常に使うdense部と一部expertをVRAM、残りの高頻度expertをpinned RAM、収まらない部分をSSDへ置く構成は既に稼働している。
重みは必要に応じて昇格・退避される。今回明示的に比較できるようにした先読みは2種類。

| オプション | 動作 | 結果の扱い |
|---|---|---|
| `--prefetch-experts 0..2` | 次層のexpertを予測しRAMからVRAMへ先行コピー | 1 expertの試験で遅くなり、既定は0を維持 |
| `--lookahead-layers 0..4` | 先の層を予測しSSDからRAMへ読み込む | 2層先読みは未使用課題で一律改善せず、既定は0を維持 |
| `--cpu-plan 012234556` | RAM上の非VRAM expert数0〜8に対応するCPU担当数を指定 | 実測候補として比較。SSD missはこの数に含めない |

先読みは計算するexpertを省略する方式ではない。予測が外れると余分な読み込み、RAMの空きslot確保、退避が増える。
先読みだけを増やせば高速になるわけではない。

## VRAM配分を待ち時間から考える

実装済みの頻度配分は各層の選択確率を正規化するため、層全体のcountを定数倍しても配分上の重みにはならない。
今回は別のオフライン計算器を作り、最初の調整課題のdecodeから、CPU待ち・expert取得・host応答待ちを層別に集計した。
miss1件あたりの平均露出時間を使い、中央値へ縮めて倍率を0.5〜2に制限し、同じ66.666GiB予算で候補slotを計算した。

後続2課題の保存済みrouteに対する、起動時固定配置の選択カバー率は、均等68.409%、頻度配分68.893%、待ち時間を加味した候補68.803%。
同じ時間倍率で重み付けしたカバー率は、頻度配分68.804%、時間を加味した候補68.838%で、差は約0.035ポイントにとどまる。
これは達成速度でも、待ち時間を実際に削減した測定でもない。平均miss単価は並列実行・同期・CPU分担の非線形性を含むため、
次のslotを追加したときの因果的な削減時間には一致しない。動的昇格・退避も再現していない。
この根拠でCUDA実装や通常の均等配分を切り替えることは見送った。候補の容量と各層枠はJSONへ保存している。

## PCIeの実測値をどう使うか

BIOS変更後のpinned DMA転送はH2D中央値36.886 GB/s、D2H中央値36.989 GB/sだった。
一方、現在のexpert取得はGPU kernelがhost-mapped RAMを直接読む経路で、DMAの測定値をそのまま当てはめられない。

14.156/16.318 MBのexpert、1/2/4/8個、grid倍率1/2/4/8およびDMA対照を3回ずつ測った。
現行grid相当のmapped readは約13.6〜21.1 GB/s、DMA対照は約18.4〜31.0 GB/s。
gridを増やしてもサイズ・個数をまたいで一貫した改善が出ず、kernel変更は採用していない。
これは単独転送の実験で、CPU laneとの同時実行や推論全体の速度を表すものではない。
検証パターンは一定byte値で、コピー範囲と末尾は確認したが、expertの入替取り違えまで識別するパターンではない。

負荷中の接続はGen5を維持した。アイドル時にGen1等へ下がる観測はあるが、変更前の「負荷中もGen1固定」とは区別する。
追加のBIOS変更、GPU reset、driver再読込は行っていない。

## Opus 5.5への相談

ユーザーの明示承認を受け、PC構成・メモリ配分・測定値をDevin CLIからClaude Opus 5.5へ送った。
Maxは600秒で回答が返らず、Highで回答を取得。実際のsessionは`shelled-seal`。ソースコード・認証情報を送らず、相談中のtool呼び出しもない。
比較後にもHighへ結果を戻し、session `literate-lavender`で再レビューを取得した。こちらもtool呼び出し0。

RAM容量、CPU校正のcache偏り、頻度と待ち時間に基づく配置、50 tokens/sに必要な帯域条件について提案を得た。
助言のうち、既に実装済みの頻度配置を新規改善と扱わず、空きVRAM全量をpoolへ追加する案もcapと安全余裕を確認せず採用しなかった。
DDR4帯域からの上限は、現在のmiss率のまま重みを毎回DRAMから読む仮定付きであり、cache hit率を改善する実装まで不可能とする証明ではない。

再レビューではDMA化が提案された。次の候補は、CPU expert処理と同時に転送してもmapped readとの差が残るかを測る事前判定。
hostへのコピー先通知、転送完了の世代管理、slotの使用終了を待つ制御が必要で、単純なcudaMemcpyAsync置換ではない。
GPU route後に記録されるeventを先にwaitするだけでは今回のコピー完了を保証できない。
実装する場合も通常は無効とし、byte列・route・配置・logit/生成の差を検査してから、CPU競合込みの速度で採否を決める。
このDMA化は今回実装していない。

## 量子化と残る目標

Unsloth方式を参考にする独自量子化は今回実行していない。現行Q4からの再量子化も行っていない。
このpackは24層がQ4 gate/up/down、18層がQ4 gate/upとQ6 down。routed expertは169.910GiB。
downを全てQ4にできたと仮定すると10.441GiB節約できるが、これは容量計算だけで、近い品質を保てることは未検証。
次に重みを変える場合は、指定Orca FP8から作り、コード・tool・日本語・長文の評価データを校正用と分離して比較する必要がある。

持続50 tokens/sには1 tokenあたり20msしか使えない。今回の測定値と、長文時のexpert領域減少を踏まえると、
先読みの設定だけで50を達成したとする根拠はない。候補は、実経路に合わせたCPU校正、cache保存形式によるVRAM節約、
品質を検証した混合量子化、対応ランタイムでのMTPであり、いずれも実装・測定前に性能保証はしない。

## 変更・検証・稼働状態

通常設定へ反映した内容はcontext **262144** とRAM headroom **16 GiB**。
CPU8 workers・自動分担、spin1ms、Pコア側0〜15、VRAM cap90 GiBとreserve2 GiB、先読み0、均等slot、600秒保持を使う。
RAM/GPU予算は通常の可変方式に戻し、比較用の固定pool・詳細trace・GPU区間計測は指定しない。
通常起動ログではRAM予算93.97 GiB、実RAM tier93.96 GiB、GPU expert pool63.13 GiBとなった。
**長文速度17.1は固定RAM94.98 GiBのベンチマーク値であり、通常設定93.96 GiBで同じ26万入力を再測定した値ではない。**
通常設定の確認は共通API1234を通した以下の短文検査による。

| 検査 | 結果 | HTTP時間 |
|---|---|---:|
| 日本語指定文の一致 | 成功 | 83.34秒（初期ロード込み） |
| clamp関数の8入力検査 | 成功 | 6.29秒 |
| lookup_assetのJSON tool call | 成功、実際のtool実行なし | 17.12秒 |

確認時、A1のPIDは反映前後で同じまま、GLMはready、空きRAM13.82 GiB、空きVRAM7.02 GiB。
GPUキューに残る1件はbrokerのcoder保持lease。試験用port1244は終了している。
GLMは通常の600秒保持に従って終了／再起動する。A1と他モデルの設定は反映前後で一致を確認した。

GLM側Python検査15件、Mang-AI登録検査1件、共通APIの機能検査3項目が成功。
モデルの再量子化やCUDA kernel変更は今回行っていない。

再登録は、準備済みのPythonからmanga-studio/scripts/configure-glm-coder.pyへ「--context 262144 --apply」を渡す。
登録スクリプト自体の既定contextは131072なので262144を明示する。
今回はバックアップ後、GPU仕事がない状態でbrokerだけを再起動して反映した。
131072へ戻す場合は「--context 131072 --apply」を使い、仕事がない状態でbrokerへ反映する。

新規CPU分担・先読みオプションは未指定なら従来の自動分担・先読み無効。不正なCPU分担表、先読み深さ、既存のメモリ・GPU lease制約を検査した。
Mang-AI登録スクリプトもCPU分担とSSD先読みを受け付ける。A1・他モデルの設定を保持する試験が成功した。
リポジトリ監査は14項目成功。変更前のファイルを保存し、適用前にSHAを照合して既存編集を保護した。
